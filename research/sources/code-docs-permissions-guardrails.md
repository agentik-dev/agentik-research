## What it says
- "Manage permissions": rules are evaluated deny first, then ask, then allow, and the first match decides; specificity does not change the order, so an allow rule cannot carve an exception out of a deny rule. A bare tool name in a deny rule (`Bash`) removes the tool from Claude's context; a scoped rule (`Bash(rm *)`) leaves the tool and blocks matching calls.
- The same section says "Permission rules are enforced by Claude Code, not by the model." Instructions in a prompt or CLAUDE.md shape what Claude tries but do not change what Claude Code allows.
- "Permission modes" table: `default` prompts on first use of each tool; `acceptEdits` auto-accepts file edits and common filesystem commands (`mkdir`, `touch`, `mv`, `cp`) in the working directory; `plan` reads and runs read-only commands; `auto` runs with a background classifier; `dontAsk` auto-denies every call that would prompt; `bypassPermissions` skips prompts except for the actions no mode auto-approves. A warning says bypass also skips prompts for writes to protected paths such as `.git` and `.claude`, and should be used only in isolated containers or VMs. `permissions.disableBypassPermissionsMode` and `permissions.disableAutoMode` set to `"disable"` lock a mode out, and are most useful in managed settings.
- "Compound commands": the recognized separators are `&&`, `||`, `;`, `|`, `|&`, `&` and newlines, and an allow rule must match each subcommand on its own. Deny and ask rules apply when any subcommand matches, including inside a subshell, a command substitution or a `for` body. A command that ends in a bare `&&` is treated as unparseable and is not split for allow matching. Up to 5 rules are saved when a compound command is approved with "don't ask again".
- "Wrappers": before matching, Claude Code strips a fixed list (`timeout`, `time`, `nice`, `nohup`, `stdbuf`, the builtins `command` and `builtin`, zsh `noglob`) and bare `xargs`. A leading assignment of a known-safe environment variable is stripped for allow rules; a deny or ask rule matches past any leading assignment, so `Bash(rm *)` in deny still matches `FOO=bar rm -rf tmp/`. The list is not configurable. Environment runners (`direnv exec`, `devbox run`, `mise exec`, `npx`, `docker exec`) are not stripped, so `Bash(devbox run *)` matches `devbox run rm -rf .`.
- "What a Bash rule doesn't match": a Bash rule matches the command text Claude writes, so it "isn't a security boundary around the program". The table shows `Bash(curl *)` missing `/usr/bin/curl` and `sh -c 'curl ...'`; `Bash(rm *)` missing `/bin/rm -rf build/` and `bash -c 'rm -rf build/'`; `Bash(git push *)` missing `git -C . push origin main`, `git -c push.default=current push origin main` and `git 'push' origin main`. For enforcement that does not depend on command text the page points to sandboxing; for your own logic over the full command text it points to a PreToolUse hook.
- A warning in the same section says Bash patterns that try to constrain arguments are fragile: `Bash(curl http://github.com/ *)` misses options before the URL, another protocol, a redirect to the allowed host, and a URL held in a variable. It suggests denying `curl` and `wget`, allowing `WebFetch(domain:...)`, and pairing the deny with the sandbox network allowlist, because a deny rule does not match the same program by path or inside `sh -c`.
- Re-opened 2026-10-14 (site sitting), claim check for the probe draft, as of October 2026. Section "Wildcard patterns": with the sample configuration (allow `Bash(npm run *)` and `Bash(git commit *)`, deny `Bash(git push *)`) Claude Code refuses commands that begin with `git push`, and a push written another way, such as `git -C . push`, is not matched. Section "What a Bash rule doesn't match" (under Bash, anchor bash-rule-limits): a Bash rule matches the command text Claude writes after compound commands are split and wrappers stripped, and its table row for `Bash(git push *)` stops `git push origin main` but not `git -C . push origin main`, `git -c push.default=current push origin main` or `git 'push' origin main`; the rows for `Bash(curl *)` and `Bash(rm *)` miss the absolute-path form and the `sh -c` or `bash -c` form. The sentence: "It doesn't match the same program invoked in a different form, so a deny or ask rule covers the invocation Claude usually produces and isn't a security boundary around the program." The section then points to sandboxing for enforcement that does not depend on command text and to a PreToolUse hook for your own logic over the full command.
- "Read-only commands": a built-in, non-configurable set (`ls`, `cat`, `echo`, `pwd`, `head`, `tail`, `grep`, `find`, `wc`, `which`, `diff`, `stat`, `du`, `cd`, read-only `git` forms) runs without a prompt in every mode. A command the analysis cannot parse prompts, and a command longer than 10,000 characters always prompts.
- "Extend permissions with hooks": PreToolUse hooks run before the permission prompt for every tool except `EndConversation`. A hook decision does not bypass rules: a matching deny rule blocks even if the hook returned allow, and a matching ask rule still prompts. A hook that exits 2 stops the call before permission rules are evaluated, even if an allow rule would have passed it. The page tells readers to allow `Bash` and register a PreToolUse hook that rejects specific commands when they want everything else to run without prompts. A user-installed "mod" that handles `tool.check` answers after rules and hooks and can approve a call a non-managed PreToolUse hook blocked.
- "Settings precedence": managed settings are highest; a deny at any level cannot be allowed by another, so a managed deny cannot be overridden by `--allowedTools`.
- "How permissions interact with sandboxing": permissions and the sandbox are complementary layers; the sandbox restrictions still apply even if a prompt injection bypasses Claude's own decision-making. With the default `autoAllowBashIfSandboxed` of `true`, sandboxed Bash runs without prompting, but explicit deny rules still apply, content-scoped ask rules still prompt, and `rm` or `rmdir` on a critical path still goes through the regular flow.
- "What runs before you trust a folder": `claude -p` and SDK sessions never show the workspace trust dialog. In that case project `permissions.allow` rules are not used (a stderr warning prints), but hooks in project settings, the `env` block and helper commands such as `apiKeyHelper` are used. To keep a repository's content out of a `-p` run the page lists `--setting-sources user`, `--bare`, and `--settings '{"disableAllHooks": true}'`.
